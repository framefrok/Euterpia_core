# Версии, ветви и Issues EUTERPIA

Документ фиксирует **как** мы делим работу на версии. Он обязателен для всех:
Issue, ветка и PR указывают свою подверсию, а порядок подверсий предсказуем.

Норма закреплена в **MANIFEST §105**; здесь — подробности, правило миграции и
примеры. Дублирование Issues запрещено: развитие оформляется ссылкой.

## 1. Две оси: линия и подверсия

- **Линия** (`v0.3`, `v0.4`, …) — тема крупного этапа. У линии есть milestone
  с человеческим названием (например «v0.3 — CLI: первый полноценный интерфейс»).
- **Подверсия** (`v0.3.1`, `v0.3.2`, …) — шаг внутри линии. Это то, что реально
  закрывается и мёржится.

Номер `vX.Y.Z`: `X.Y` — линия, `Z` — шаг. Версия пакета
(`euterpia_version.nim`) поднимается на шаге, который этого заслуживает
(обычно `.1` — релизная механика — или последний закрытый шаг линии).

## 2. Смысл шага `Z` (жёстко)

| шаг | что входит | метки-подсказки |
|---|---|---|
| `.1` | **организация и документация**: README, MANIFEST, `euterpia_version`, шаблоны, релизная механика (CHANGELOG, артефакты, установка) | `docs`, `chore`, `ci` |
| `.2` | **критическое и архитектурное**: P0/P1-ошибки, крупные архитектурные изменения, снятие блокеров | `architecture`, `tech-debt`, `bug`+`p0/p1` |
| `.3` | функциональность **P1** | `feature`+`p1` |
| `.4` | функциональность **P2** | `feature`+`p2` |
| `.5` | функциональность **P3** и полировка | `feature`+`p3` |
| `.6`… | только если линия переросла; снова по смыслу, не «до круглого» | — |

Порядок **не перескакивает**: `.1` (организовать) → `.2` (фундамент и критика)
→ `.3/.4/.5` (функции по приоритету). Нельзя в одной подверсии делать крупную
архитектуру, а в следующей — рисовать кнопки: сначала логика и фундамент, потом
форма.

## 3. Объём подверсии

Подверсия должна **закрываться целиком**. Ориентир — то, что реально проходит
ревью и CI за один цикл. Дробить на десятки микро-релизов нельзя; если шаг
разросся, его делят **по теме** (например `.3` — транспорт, `.4` — запись), а
не по счётчику. Потолка номера нет (`v0.3.99` допустим), но «99» — признак, что
линию пора переосмыслить, а не дробить дальше.

## 4. Ветви

Ветвь повторяет подверсию и тип работы:

```text
docs/v0.3.1-release-notes      # организация
fix/v0.3.2-param-flags         # критическое
feat/v0.3.3-transport          # P1
feat/v0.4.4-views              # P2
```

`main` содержит только то, что прошло CI и ревью. Стековые PR допустимы
(`A → B → main`), но каждая ветвь несёт свою подверсию.

## 5. Правило привязки Issue к подверсии

Issue получает milestone по меткам (правило MANIFEST §105.6):

1. есть `docs` или `chore`, либо `ci` **без** `feature` → шаг **`.1`**;
2. есть `architecture` (или `bug` с `p0`/`p1`) → шаг **`.2`**;
3. иначе по приоритету: `p1 → .3`, `p2 → .4`, `p3 → .5`.

Это правило применяется к **открытым** Issues линии. Закрытые Issues остаются на
своих milestone как история. Milestone линии (`v0.3`) сохраняется как «зонтик»:
после миграции в нём не должно оставаться открытых Issues.

## 6. Не дублировать: ссылаться и конкретизировать

Плохо:

> «улучшить EUT plugin» (новая Issue)

Хорошо (продолжение направления ссылкой):

> См. #NNN. Развитие: `adapters/eut/eut_plugin.nim:120-180` — сейчас state
> сохраняется целиком при каждом `setParam`; нужно инкрементально, потому что
> на больших патчах это аллокации в control-path. Оставить `EUT_Event`, убрать
> дублирующий буфер, добавить тест round-trip.

Правило: **файл + строки + выписка кода + что не устраивает + что
добавить/удалить и почему**. Следующая подверсия продолжает направление
ссылкой на исходную Issue, а не копией.

## 7. Миграция (как это делается сейчас)

1. Для линии создаются подверсии-milestone (`vX.Y.1`…`vX.Y.5` по мере надобности).
2. Открытые Issues линии переразмечаются по правилу §5 (скриптом по меткам).
3. Неразмеченные Issues сначала попадают в линию по смыслу (какая тема), затем —
   в подверсию по правилу §5.
4. В зонтичном milestone линии не остаётся открытых Issues.

Инструмент: `tools/reassign_milestones.py` (по умолчанию сухой прогон, запись —
`--apply`). Карта линий для неразмеченных Issues задана в `LINE_OF`; её правят
по мере появления новых тем.

**Статус (v0.3–v0.7):** выполнено — 182 открытых Issues разложены по 24
подверсиям; зонтичные milestone (`v0.3`…`v0.7`) содержат 0 открытых Issues.
Линия определяется по существующему milestone, шаг — по меткам.

## 8. Примеры привязки (из текущего реестра)

- `[P1][core][control] Control Core: единая командная модель` → **v0.3.2**
  (архитектура).
- `[P1][cli] Транспорт: transport tempo/position/...` → **v0.3.3** (P1-функция).
- `[P2][cli] Экспорт стемов и батч-рендер` → **v0.3.4** (P2-функция).
- `[P3][cli][docs] Справочник CLI` → **v0.3.1** (документация).
- `[P1][nodes][audio][bug] Инструмент копит scratch` → линии **v0.7**
  («глубина»: инструменты), шаг `.2` (критическая ошибка).

## 9. Как добавить линию

Новая линия создаётся, когда тема не помещается в существующие. Milestone
названия линии — `vX.Y — <тема>`, подверсии — `vX.Y.Z — <шаг>`. Правило смысла
шагов (§2) действует и здесь.
