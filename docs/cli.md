# CLI EUTERPIA — справочник

`euterpia` — первый полноценный интерфейс ядра (линия v0.3). CLI —
**равноправный клиент** Core (§60), а не «второй Core»: он не содержит
бизнес-логики и ходит в ядро только через публичные API (§20, §63).

CLI обязан быть `machine-readable` и `composable` (MANIFEST §19-§21):
человекочитаемый вывод для человека, `--json` для агента и скриптов,
никаких «полуструктурированных» форматов.

- Точка правды о поверхности команд — спецификация `libs/cli_spec` (#330):
  из неё строятся `--help`, `help --json`, автодополнение и раздел
  «Справочник команд» ниже (генерируется `nimble cliDocs`).
  `--help` и `help --json` строятся из него, поэтому не расходятся (#96).
- Проверить машинную справку: `euterpia help --json`.
- Исходная задача: [#96](https://github.com/framefrok/Euterpia_core/issues/96).

## Файл проекта и его расширение

Файл проекта — `.eproj`: это расширение по умолчанию (`euterpia init` создаёт
`project.eproj`), и его понимают команды при разборе позиционного аргумента
(`euterpia render demo.eproj`).

Историческое `.eut` принимается наравне: расширение — **подпись файла, а не
часть формата**. Тип файла ядро определяет по содержимому (`format` =
`euterpia-project`, `core/project.nim`), поэтому `mv demo.eut demo.eproj` ничего
не ломает и миграции не требует (MANIFEST §19/§58/§59). Список расширений один
на все команды и живёт в `cli/cmd_project.nim` (`ProjectSuffixes`), поэтому
команды не могут разойтись в том, какой аргумент считается файлом проекта.

Позиционный аргумент с другим расширением файлом проекта не считается:
`euterpia node list notes.json` — ошибка использования, а не попытка открыть
`notes.json` как проект.

Примеры-пьесы `compositions/*` намеренно **остаются** с `.eut`: так историческое
расширение остаётся проверенным живым примером (`compositions/*/build_via_cli.sh`
передаёт `ensemble_cli.eut` в CLI), а не только обещанием в документации.

## Грамматика вызова

```text
euterpia [глобальные ключи] <команда> [аргументы команды]
euterpia [глобальные ключи] <команда> [--] [аргументы]
euterpia help [команда]
euterpia --version
```

- Глобальные ключи распознаются **и до, и после** имени команды
  (`euterpia --json node list` и `euterpia node list --json` — одно и то же).
- `--` прекращает разбор ключей: всё после него команда получает как есть.
- Запуск без аргументов печатает справку и завершается кодом 0 — это
  ответ на вопрос, а не ошибка.

## Режимы вывода

| Режим | Как включить | Куда что идёт |
|---|---|---|
| human (умолчание) | `--human`, настройка `output=human` | результат — строки в **stdout** |
| json | `--json`, настройка `output=json` | ровно **одна строка JSON** в stdout |

Правила (закреплены в `cli/context.nim`):

- **stdout — только результат команды.** Логи Core, предупреждения и
  ошибки идут в **stderr**; иначе `--json` перестал бы быть парсируемым.
- Вывод **детерминирован**: нет времени и случайных значений, повторный
  запуск даёт байт-в-байт тот же результат (критерий приёмки #88).
- Приоритет режима и настроек: **argv > env (`EUTERPIA_*`) > файл
  настроек > умолчание** (#258). Источник значения показывает
  `euterpia config get <ключ>`.

## JSON-конверт

Машинный ответ — версионированный конверт (`schema`), поля нагрузки
лежат **рядом** с ним, а не во вложенном объекте (MANIFEST §21):

```json
{
  "schema": 1,
  "ok": true,
  "command": "version",
  "exitCode": 0,
  "name": "euterpia",
  "version": "0.3.2"
}
```

- `schema` — версия схемы конверта. Меняется только при несовместимом
  изменении полей: клиент обязан заметить, что схема другая.
- `ok` — инвариант `ok == (exitCode == 0)`. Агенту достаточно одного поля.
- `command` — имя команды, к которой относится ответ.
- `exitCode` — тот же код, что вернул процесс (не «результат в JSON»).
- При ошибке добавляются `errorCode` и объект `error`:

```json
{
  "schema": 1,
  "ok": false,
  "command": "param",
  "exitCode": 1,
  "errorCode": 4,
  "error": {
    "kind": "out_of_range",
    "message": "gain = 99.0 вне диапазона 0.0…2.0",
    "hint": "диапазон объявлен типом ноды: euterpia.gain"
  }
}
```

`error.kind` — **код причины** из control-слоя (`ErrorCode`, issue #139): `usage`
-объект больше не описывает класс ошибки, а называет конкретную причину
(`not_found`, `already_exists`, `out_of_range`, `unknown_node_type`,
`unknown_parameter`, `duplicate_connection`, `port_kind_mismatch`,
`no_descriptor`, `unsupported_command`, `api_version_mismatch`, …). Для ошибок
самой CLI (неизвестная команда, битый аргумент) код остаётся классом:
`usage`, `env`, `panic`.

`errorCode` — тот же код числом: агент различает причины, не разбирая текст.
Классы ошибок при этом не потеряны: по `errorCode` CLI возвращает прежний код
процесса (данные → 1, среда → 2, баг → 3).

## Коды возврата

| Код | Значение | Пример |
|---|---|---|
| 0 | успех | команда выполнена |
| 1 | ошибка данных или использования | неизвестная команда/ключ, лишний аргумент, значение вне диапазона, провал `project validate` |
| 2 | ошибка среды | нет библиотеки, аудиоустройства или прав; недоступный бэкенд |
| 3 | внутренняя ошибка (баг CLI) | необработанное исключение; просьба приложить `euterpia --version` |

`doctor` возвращает 0, если нет провалов проверок, и 2 — если есть.
`analyze --fail-on <уровень>` возвращает 1 при дефектах не ниже уровня.

Класс отказа виден в `error.kind` (`usage`, `env`, `io`, `defects`, `panic`…),
а **точная причина** — числом `errorCode`. Соответствие «причина → код
возврата» живёт данными в `cli/exit_codes.nim` (issue #332): таблица целиком —
в разделе «Справочник команд» ниже и в машинном виде в `help --json`
(`errorReasons`). Добавленная в ядро причина без строки в таблице роняет CI,
поэтому документация не может отстать от кода.

| Ключ | Назначение |
|---|---|
| `--json` | машиночитаемый вывод: ровно одна строка JSON в stdout |

### `init` — создать проект: метаданные и пустой граф

```text
euterpia init [файл] [ключи]
```

Аргументы:

- `файл` — проект: *.eproj или *.eut; по умолчанию project.eproj

Ключи:

| Ключ | Значение | Умолчание | Смысл |
|---|---|---|---|
| `--name` | строка | — | имя проекта; без ключа имя берётся из имени файла |
| `--author` | строка | — | автор проекта |
| `--sr`, `--sample-rate` | Гц | 48000 | частота дискретизации проекта |
| `--tempo` | число BPM | 120 | темп проекта |
| `--ts`, `--time-signature` | числитель/знаменатель | 4/4 | размер такта |
| `--force` | — | — | перезаписать существующий файл |

Пример:

```text
euterpia init demo.eproj --name Demo --tempo 140
```

Поля ответа `--json`:

- `path` — куда записан проект
- `documentId` — идентификатор документа: адреса одного файла отличимы от другого (#143)
- `format` — имя формата файла — по нему ядро и узнаёт проект (§58)
- `version` — версия формата
- `metadata` — имя, автор, темп, частота дискретизации, размер
- `graph` — ноды и связи (после `init` пустые)
- `sequencer` — треки, клипы и автоматизация
- `pluginStates` — состояния плагинов
- `summary` — счётчики: ноды, связи, треки, клипы

Подробности:

- граф создаётся пустым: ноды добавляет `euterpia node add` (#90)
- существующий файл не затирается: перезапись требует --force
- расширение — подпись файла, а не формат: историческое `.eut` принимается наравне с `.eproj`, а тип файла ядро определяет по содержимому (§19/§58)

### `project` — показать, изменить или проверить файл проекта

```text
euterpia project <show|set|validate>
```

Подкоманды: show | set | validate | recover

Аргументы:

- `файл` — проект: *.eproj или *.eut; по умолчанию project.eproj
- `поле значение` — только `project set`: name, author, tempo, sample-rate, time-signature

Ключи:

| Ключ | Значение | Умолчание | Смысл |
|---|---|---|---|
| `--list` | — | — | `project recover`: перечислить снимки автосохранения |
| `--from` | файл | — | `project recover`: конкретный снимок |

Пример:

```text
euterpia project show demo.eproj
```

Поля ответа `--json`:

- `path` — путь прочитанного проекта
- `documentId` — идентификатор документа (#143)
- `metadata` — имя, автор, темп, частота, размер
- `graph` — ноды и связи
- `sequencer` — треки, клипы и автоматизация
- `pluginStates` — состояния плагинов
- `summary` — счётчики: ноды, связи, треки, клипы
- `change` — что изменил `project set`: поле, до и после
- `sections` — результат `project validate`: секции и проверки
- `snapshots` — `project recover --list`: снимки автосохранения
- `version` — версия восстановленного снимка
- `backup` — резервная копия пользовательского файла перед восстановлением
- `written` — файл проекта записан восстановлением

Подробности:

- project show [файл] — метаданные, граф, треки/клипы, автоматизация, состояния плагинов
- project set [файл] <поле> <значение> — поля: name, author, tempo, sample-rate, time-signature
- project set пишет атомарно (tmp + rename) и обновляет metadata.modified
- project validate [файл] — отчёт о формате и целостности: провал проверки даёт код 1
- project recover [файл] — восстановить последний снимок автосохранения (маркер аварии)
- project recover --list — перечислить снимки; --from <файл> — конкретный снимок
- перед восстановлением файл пользователя копируется в `<проект>.bak`
- без файла команды работают с `project.eproj` — как в примере MANIFEST §19

### `midi` — MIDI: экспорт проекта в SMF, список портов и монитор событий

```text
euterpia midi <проект.eproj> [--out файл.mid] [--split каталог] | midi import <проект> <файл.mid> | midi list | midi monitor [--in N] [--seconds S]
```

Аргументы:

- `проект.eproj` — что экспортировать; историческое `.eut` принимается
- `подкоманда` — `list` — порты входа/выхода; `monitor` — поток событий

Ключи:

| Ключ | Значение | Умолчание | Смысл |
|---|---|---|---|
| `--out` | файл.mid | — | куда записать один файл формата 1 |
| `--split` | каталог | — | по файлу на инструмент (формат 0) |
| `--in` | N | — | порт входа для `monitor` (индекс из `midi list`) |
| `--seconds` | секунды | — | сколько слушать `monitor`; без ключа — до SIGINT |
| `--channel` | N | — | фильтр `monitor` по MIDI-каналу 1…16 |
| `--only` | типы | — | фильтр `monitor` по типу: note,cc,pitchbend,aftertouch,program |
| `--track` | N | — | `import`: дорожка проекта (по умолчанию — в конец) |
| `--map` | SMF:проект | — | `import`: сопоставление SMF:проект (можно несколько) |

Пример:

```text
euterpia midi ensemble.eproj --out ensemble.mid
```

Поля ответа `--json`:

- `project` — прочитанный проект (экспорт)
- `files` — записанные файлы (при `--dry-run` — план)
- `tracks` — сколько дорожек попало в файлы
- `notes` — сколько нотных событий выгружено
- `backend` — имя MIDI-адаптера (`midi list`/`monitor`)
- `inputs` — порты входа `midi list`
- `outputs` — порты выхода `midi list`
- `events` — сколько событий напечатал `monitor`
- `importedTracks` — `import`: сколько SMF-дорожек попало в проект
- `importedNotes` — `import`: сколько нот создано
- `ignoredEvents` — `import`: CC/PB и прочее, что формат клипа не хранит
- `ppq` — `import`: разрешение SMF и пересчёт в PPQ проекта
- `tempo` — `import`: темп из SMF, записанный в проект

Подробности:

- формат 1: дорожка-дирижёр (имя, темп, размер) + по дорожке на каждый непустой трек
- --split: по файлу на инструмент (формат 0), имя начинается с номера дорожки
- если не указан ни --out, ни --split: рядом пишется `<проект>.mid`
- тики проекта и SMF совпадают по разрешению (PPQ), позиции не пересчитываются
- клипы раскрываются как в движке: Note Off обрезается границей клипа, зацикленный клип повторяется до конца песни
- --dry-run печатает план и не пишет файлов
- `midi list`: нет librtmidi — пустой список и код 0; это «адаптера нет», а не ошибка данных
- `midi monitor` печатает относительное время от открытия порта (без времени суток)
- `--json` у monitor — NDJSON: одна строка на событие, затем итоговый конверт
- `midi import` берёт ноты, имя дорожки, первый темп и размер; PPQ пересчитывается в 960
- CC/PB/aftertouch/program не входят в формат клипа: их число печатается в `ignoredEvents`
- SMF format 2, SMPTE-тайминг и несколько темпов/размеров отвергаются явно
- `--map SMF:проект` адресует дорожки; `--track N` — только для одной дорожки
- импорт — одна транзакция истории: `euterpia undo` возвращает проект до него
- раскодировать обратно можно тем же кодеком: `commons/midi_io.parseSmf`

### `plugin` — внешние плагины: scan/info/params/save/validate

```text
euterpia plugin <scan|info|params|save|validate> [аргументы] [ключи]
```

Подкоманды: scan | info | params | save | validate

Аргументы:

- `подкоманда` — scan | info | params | save | validate
- `аргументы` — путь к .clap/каталогу или проект и id ноды

Ключи:

| Ключ | Значение | Умолчание | Смысл |
|---|---|---|---|
| `--index` | N | — | индекс плагина в библиотеке (по умолчанию 0) |
| `--validator` | путь | — | путь к clap-validator (иначе поиск в PATH) |

Пример:

```text
euterpia plugin scan /usr/lib/clap --json
```

Поля ответа `--json`:

- `subcommand` — выполненная подкоманда
- `files` — библиотеки/бандлы, которые просмотрены
- `plugins` — найденные плагины: id, name, vendor, порты, параметры
- `plugin` — подробности одного плагина (`info`)
- `node` — нода проекта (`params`/`save`)
- `params` — параметры инстанса: id, имя, значение
- `state` — сохранённое состояние: bytes, sha1 (`save`)
- `validator` — путь и код возврата внешнего валидатора
- `checks` — проверки валидатора: id, status, message
- `passed` — валидатор: все проверки пройдены
- `failed` — валидатор: сколько проверок упало

Подробности:

- нет CLAP-адаптера — код 2, а не паника: `plugin scan` честно говорит, чего нет
- `save` пишет непрозрачный блоб состояния в проект; байты в `project show` не печатаются — только размер и хеш
- `validate` не подменяет валидатор своим кодом: нет инструмента — код 2 с подсказкой установки (#260)
- валидатор запускается на control-path; аудиоустройство не открывается, плагин в процесс CLI не грузится (#260)

### `transport` — транспорт: темп, размер, позиция, воспроизведение, цикл

```text
euterpia transport <подкоманда> [аргументы] [проект.eproj] [ключи]
```

Подкоманды: tempo | meter | position | seek | play | pause | stop | loop | state

Аргументы:

- `<подкоманда>` — tempo|meter|position|seek|play|pause|stop|loop|state
- `проект.eproj` — проект; без аргумента — `project.eproj`, если он есть

Ключи:

| Ключ | Значение | Умолчание | Смысл |
|---|---|---|---|
| `--file` | проект.eproj | — | проект, если он не задан позиционно |
| `--unit` | bbt|seconds|frames | bbt | единица позиции для seek/loop set |
| `--seconds` | — | — | то же, что `--unit seconds` |
| `--frames` | — | — | то же, что `--unit frames` |

Пример:

```text
euterpia transport tempo 140 demo.eproj
```

Поля ответа `--json`:

- `schema` — версия схемы ответа: `euterpia.transport.v1`
- `state` — состояние: `stopped`|`playing`|`recording`|`paused`
- `position` — позиция: `frames`, `seconds`, `bar`, `beat`, `tick`, `quarter`
- `tempo` — темп в BPM
- `meter` — размер такта: `numerator`, `denominator`
- `loop` — цикл: `enabled`, `startFrames`, `endFrames`
- `metrics` — метрики: `xruns`, `cpuLoad` (offline — `null`)
- `path` — проект, если команда его читала или меняла
- `change` — что изменил `tempo`/`meter`: поле, до и после

Подробности:

- `tempo` и `meter` меняют ДОКУМЕНТ проекта: `transport tempo 140` + `render` учитывает новый темп
- `play`/`pause`/`stop`/`seek`/`loop` меняют offline-сессию рядом с проектом (живого устройства нет — это #92)
- позиция BBT ↔ кадры и длительности такта считает ядро (`core/transport`); CLI формул не копирует
- `position` — чтение, `seek` — запись: одна команда не совмещает get и set
- пауза сохраняет позицию, стоп возвращает в 0 (#257)
- `metrics.cpuLoad` в offline равен null: реальную загрузку предоставит живой backend (#92)
- `--dry-run` печатает план и не пишет ни проект, ни сессию

### `session` — headless runtime-сессия: запуск, остановка, состояние

```text
euterpia session <подкоманда> [проект.eproj] [ключи]
```

Подкоманды: start | stop | status

Аргументы:

- `<подкоманда>` — start|stop|status
- `проект.eproj` — проект; без аргумента — `project.eproj`, если он есть

Ключи:

| Ключ | Значение | Умолчание | Смысл |
|---|---|---|---|
| `--file` | проект.eproj | — | проект, если он не задан позиционно |

Пример:

```text

```

Поля ответа `--json`:

- `running` — сессия жива (`true`) или нет
- `pid` — pid демона
- `socket` — путь Unix-сокета сессии
- `project` — проект, к которому привязана сессия
- `sampleRate` — частота сессии
- `blockSize` — размер блока
- `state` — состояние транспорта: `stopped`|`playing`|`paused`|`recording`

- `autosaveMs` — период автосохранения демона (0 — выключено)

Подробности:

- сессия живёт между вызовами CLI: `transport play` в одном запуске виден `transport state` в другом (#407)
- демон владеет AudioEngine; `session stop` уничтожает движок и закрывает сокет
- адрес — Unix-socket 0600 в `/tmp`; файл `<проект>.session.json` только указывает на него
- без проекта сессия привязана к текущему каталогу и умолчаниям ядра (120 BPM, 4/4, 48 кГц)
- `session stop` записывает финальное состояние в offline-сессию транспорта: после остановки `transport state` не врёт

Аргументы:

### `render` — офлайн-рендер проекта в WAV без аудиоустройства

```text
euterpia render [проект.eproj] [выход.wav] [ключи]
```

Аргументы:

- `проект.eproj` — что рендерить; историческое `.eut` принимается
- `выход.wav` — куда писать; без аргумента — рядом с проектом

Ключи:

| Ключ | Значение | Умолчание | Смысл |
|---|---|---|---|
| `--file` | проект.eproj | — | проект, если он не задан позиционно |
| `--out` | файл.wav | — | файл вывода, если он не задан позиционно |
| `--seconds` | секунды | — | длительность рендера; без ключа — конец последней ноты плюс --tail |
| `--tail` | секунды | 2 | добавка после последней ноты, секунды |
| `--master` | id ноды | — | id ноды, подключённой к мастеру; без ключа мастер определяется по графу |
| `--solo-track` | id дорожки | — | рендерить только эту дорожку (стем, #209) |
| `--stems` | каталог | — | стемы: по WAV на дорожку в указанный каталог (#108) |
| `--name-template` | шаблон | {track}_{name}.wav | шаблон имён стемов: {track}, {name}, {index} |
| `--batch` | файл | — | список проектов для последовательного рендера (#108) |
| `--sample-rate` | Гц | — | частота дискретизации; без ключа — из проекта, затем настройки |
| `--block` | кадры | 512 | размер блока обработки |
| `--bits` | 16, 24 или 32 | 16 | глубина дискретизации WAV |
| `--progress` | — | — | показывать прогресс в stderr (по умолчанию — только если stderr это терминал) |
| `--no-progress` | — | — | не показывать прогресс |

Пример:

```text
euterpia render project.eproj song.wav --seconds 30
```

Поля ответа `--json`:

- `path` — отрендеренный проект
- `out` — записанный WAV (или план при `--dry-run`)
- `format` — формат вывода: `wav`
- `formatDescription` — расшифровка формата
- `channels` — число каналов (стерео)
- `sampleRate` — частота дискретизации рендера
- `blockSize` — размер блока обработки
- `bitsPerSample` — глубина дискретизации
- `seconds` — итоговая длительность
- `scoreSeconds` — длительность партитуры без хвоста
- `tailSeconds` — добавленный хвост
- `tempo` — темп, по которому считались тики
- `songEndTick` — конец песни в тиках
- `frames` — кадров на канал
- `rendered` — отрендерено кадров
- `dryRun` — план без записи
- `masterNodeId` — нода, выбранная мастером
- `soloTrack` — id дорожки для стема (0 — мастер-микс)
- `noteNodes` — ноды с нотными событиями
- `automationLanes` — дорожки автоматизации, попавшие в рендер
- `issues` — замечания рендера (не ошибки)
- `peak` — пиковый уровень записанного WAV
- `rms` — среднеквадратичный уровень
- `silent` — запись тишины — предупреждение, а не ошибка
- `stems` — стемы: `track`, `name`, `file`, `frames`, `ok` (#108)
- `stemsFailed` — сколько стемов не отрендерилось
- `batch` — результаты батча: `project`, `out`, `ok`, `exitCode`
- `batchFailed` — сколько проектов батча не отрендерилось

Подробности:

- пример MANIFEST §19: euterpia render project.eproj
- вывод — WAV (PCM 16, 24 или 32 бита, стерео); MP3/OGG требуют кодировщика и в ядре отсутствуют
- проект без нотных событий требует --seconds: длину пустой партитуры CLI не выдумывает
- частота и блок: argv > метаданные проекта > настройки > умолчание
- --stems <каталог>: по WAV на дорожку; имена из --name-template ({track}, {name}, {index})
- стемы рендерятся тем же путём, что и мастер, с --solo-track; mute/solo дорожек учитываются
- --batch <файл>: строки «проект [выход][ --seconds N]», # — комментарий; --out задаёт каталог
- батч идёт последовательно: сцена и движок освобождаются после каждого проекта
- если хоть один стем/проект упал — ненулевой код, отчёт перечисляет удачные и неудачные
- --dry-run печатает план рендера и не пишет файл
- индикатор прогресса идёт в stderr: проценты, прошлое, осталось и скорость (×REALTIME)
- по умолчанию он включается, только если stderr — терминал: в CI и пайпах вывод остаётся байт-в-байт тем же
- --progress / --no-progress решают явно; -q отключает
- тихая или оборванная запись — предупреждение, а не ошибка: код 2 только у сбоя записи

| `--format` | wav|flac|ogg|mp3 | wav | формат сдачи: wav|flac (lossless) или ogg|mp3 (превью) |
| `--preview-bitrate` | кбит/с | 192 | битрейт lossy-превью, кбит/с |
| `--dir` | каталог | — | каталог сдачи (мастер + стемы + манифест) |

| `--master` | id ноды | — | id мастер-ноды проекта |

Пример:

```text

```

Поля ответа `--json`:

- `input` — вход: проект или WAV
- `out` — файл мастера
- `format` — формат вывода: wav|flac|ogg|mp3
- `codec` — кодек результата: pcm|flac|vorbis|mp3
- `lossless` — lossless-сдача (wav/flac) или превью
- `role` — `master` (сдача) или `preview`
- `bitrate` — битрейт превью, кбит/с (0 у lossless)
- `bitsPerSample` — глубина итогового файла
- `sampleRate` — частота
- `dither` — включён ли TPDF-dither
- `targetLufs` — цель нормализации
- `ceilingDb` — потолок true peak
- `inputLufs` — громкость входа
- `outputLufs` — громкость результата
- `gainDb` — усиление по громкости
- `appliedGainDb` — итоговое усиление
- `truePeakDb` — true peak результата
- `samplePeakDb` — sample peak результата
- `limitedFrames` — кадров, затронутых лимитером
- `lra` — динамический диапазон (LRA, LU)
- `stems` — стемы: имя, файл, метрики
- `manifest` — манифест сдачи с хешами файлов
- `metadata` — записанные метаданные

Подробности:

- метрики — BS.1770/EBU R128: LUFS, short-term, LRA, true peak (×4 oversampling) (#209)
- dither — TPDF, детерминированный: повторная сдача даёт те же байты
- стемы рендерятся по дорожкам проекта (render --solo-track) и суммируются в мастер
- манифест содержит SHA-1 каждого файла: это контроль целостности пакета, не подпись
- FLAC пишется встроенным lossless-энкодером (#411); OGG/MP3 — превью через ffmpeg/lame/oggenc
- для lossy-превью dither не применяется: шум квантования не имеет смысла перед сжатием

- `metrics` — измерения: пик, RMS, DC offset, уровень шума
- `defects` — найденные дефекты с локализацией: время, кадр, уровень
- `summary` — сводка по уровням дефектов
- `error` — причина отказа (не WAV, нет файла)
- `errorCode` — код причины отказа — по нему выбирается код возврата (#332)

Подробности:

- читает WAV и печатает отчёт с локализацией: клиппинг, DC, щелчки, провалы, зависание, жужжание 50/60 Гц, алиасинг, резкость
- вердикт «нравится» остаётся за слушателем: инструмент не судит музыку, а указывает конкретные места и причины
- --fail-on info|warn|error — порог для CI: код 1 при дефектах не ниже уровня
- --snippets <каталог> пишет короткие WAV вокруг дефектов, --heatmap <файл.pgm> — спектрограмму
- тот же Core-API (`core/audio_inspect`) позже использует Editor (#178)

## Адреса сущностей (handle, #143)

```text
euterpia node list                        # в списке: #3 Filter [node:3.1]
euterpia node list --json                 # "handle": "node:3.1",
                                          # "handleRef": "node:3.1@4d379bc5"
euterpia param list 3                     # freq = 440 (node:3.1/param:1)
euterpia node show node:3.1               # та же нода по адресу
euterpia param get 3 node:3.1/param:1     # тот же параметр по адресу
```

- Форма адреса: `вид:слот.поколение`, где слот — постоянный `id` сущности в
  проекте, а поколение растёт при переиспользовании слота ([#143](https://github.com/framefrok/Euterpia_core/issues/143),
  MANIFEST §35/§36).
- Полная форма `вид:слот.поколение@документ` дополнительно называет документ:
  адрес из другого файла отвергается, а не «случайно подходит» (`project show`
  печатает `документ: <ид>` и `documentId` в `--json`).
- Вложенные сущности адресуются путём: `node:3.1/component:1/param:0` —
  «подграф → компонент → параметр»; клип — `track:1.1/clip:0`, потому что его
  `id` уникален только внутри дорожки.
- Адрес устойчив к правкам графа: вставка ноды не сдвигает адреса уже
  напечатанных, а удалённая нода адреса не имеет («в документе нет ноды с
  адресом …»).
- В отчёте код отказа адресации печатается числом: 1 — не разобран, 2 — чужой
  документ, 3 — просрочен, 5 — удалён, 6 — не тот вид сущности.

## Индикатор прогресса рендера (#310)

**Индикатор прогресса.** Длинный рендер показывает в **stderr** проценты,
отрендеренное/всего, прошедшее, оставшееся и скорость (`×29.0` — во столько
быстрее реального времени) с «вращающейся палочкой»:

```text
⠸ рендер 98% · 59:27 / 59:55 · прошло 2:03 · осталось 0:01 · ×28.9
```

По умолчанию он включается **только если stderr — терминал**: в CI и пайпах
вывод остаётся байт-в-байт детерминированным, а stdout — только отчёт.
`--progress` / `--no-progress` решают явно, `-q` отключает, `--dry-run`
не показывает ничего (диск не трогаем).

## Сценарии

Сценарии выполняются как написано (копипаст). Роль `euterpia` — собранный
`build/euterpia` или установленный в PATH.

### Создать проект, собрать граф и отрендерить (§19)

```bash
euterpia init song.eproj --name "Demo" --tempo 100

euterpia node add oscillator --file song.eproj --name osc
euterpia param set osc freq 220 --file song.eproj
euterpia node add gain --file song.eproj --name out
euterpia connect osc:out out:in --file song.eproj
euterpia param set out level 0.5 --file song.eproj

euterpia graph check --file song.eproj          # компиляция через Core
euterpia render song.eproj out.wav --seconds 3 # офлайн-рендер, без устройства
euterpia analyze out.wav --fail-on error      # инспектор для CI
```

Машинный вариант любого шага: добавить `--json`.

### Импортировать партитуру и отдать наружу

```bash
cat > motif.notes <<'EOF'
c4/4 d e f | g/2 r/2
EOF

euterpia notation check motif.notes
euterpia notation import motif.notes --file song.eproj --track 0 --name Lead
euterpia midi song.eproj --out song.mid
```

### Проверить окружение перед живым запуском

```bash
euterpia doctor                 # человеку
euterpia doctor --json | jq .   # агенту: сводка, секции, факты
euterpia config get backend     # откуда взялось значение
```

## Согласованность документации и кода

Справочник обязан **не расходиться** с кодом (#96). Это обеспечивается
структурно, а не дисциплиной:

- описание команды живёт **данными** — спецификацией `libs/cli_spec`
  ([#330](https://github.com/framefrok/Euterpia_core/issues/330)): имя, синопсис,
  ключи с типами значений и умолчаниями, пример вызова, поля ответа `--json`;
- из одной спецификации строятся четыре представления: `--help`,
  `help --json` (машинная схема), кандидаты автодополнения `__complete` и
  **этот раздел** — он генерируется между маркерами
  `<!-- cli-spec:begin … -->` / `<!-- cli-spec:end -->` командой
  `nimble cliDocs` (`euterpia __reference --write docs/cli.md`);
- `tests/cli_test.nim` сверяет раздел в репозитории со свежим выводом
  `__reference` **байт-в-байт**, прогоняет `cli_spec.validateSpecs` по боевому
  реестру (пустой список замечаний — описания полны) и проверяет, что каждый
  объявленный ключ действительно принимается разбором команды, а каждый
  названный в `--json`-схеме — приходит в ответе;
- поэтому «поправить справку руками» невозможно: правится спецификация,
  раздел пересобирается, а расхождение роняет CI, а не проходит молча;
- паритет с интерфейсом Editor — предмет отдельной сверки: каждая видимая
  команда либо покрыта действием клиента, либо объяснена, почему она только
  для CLI. Правила и перечень — [clients.md](clients.md) (#148), проверка —
  suite «паритет клиентов» в `tests/cli_test.nim`.
