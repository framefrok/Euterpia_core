# План шага v0.3.2 — «Критическое и архитектурное»

Шаг `.2` линии v0.3 (MANIFEST §105, `docs/versions.md` §2): **P0/P1-ошибки,
крупные архитектурные изменения и снятие блокеров.** Порядок не перескакивает:
сначала фундамент управления и адресации (Logic), затем форма (v0.3.3+).

Источники: milestone v0.3.2 и Issues #292, #139, #141, #143, #148, #213, #5,
#50, #86. Дублировать Issues запрещено — этот документ только **упорядочивает**
их и фиксирует зависимости/критерии (§7 docs/versions.md).

## Принцип шага

Клиент (CLI, будущий Editor, встраивание) не должен знать внутренностей ядра
(§20, §63). Сегодня команды CLI пишут прямо в компоненты, а чтения/адресации
как публичного контракта нет. Шаг вводит **Control Core** (командная модель №65),
**Query API** (чтение модели), **стабильные handle-ID** и **паритет клиентов** —
чтобы CLI и Editor исполняли одни и те же команды, а не дублировали логику.

## 1. #292 — флаги параметров как битовая маска

- **Симптом:** `param set <нода> <параметр> 0.62` → «параметр целочисленный»;
  `param get` печатает неверные флаги (`automatable+modulatable` → `modulatable+choice`).
- **Причина:** `nodes/sdk/node_api.nim`, `NodeParamFlag` — enum без явных
  значений (`npfAutomatable=0, npfModulatable=1, npfInteger=2, npfChoice=3`),
  но весь код читает/пишет флаги как битовую маску (`flags and uint32(flag)`).
- **Объём:**
  - явные значения-степени двойки у `NodeParamFlag`;
  - `NodeParamFlagOrder` (enum с «дырками» в Nim не итерируем);
  - unit-тест на независимость битов;
  - CLI-тест: `param set` принимает дробное и отрицательное в диапазоне типа;
    `param get` показывает корректные флаги.
- **ABI:** изменение значений enum меняет сериализацию флагов в `.eut`. Проверить
  версию/миграцию формата (§58); при необходимости — читать старую маску как есть.
- **Критерии:** дробные/отрицательные значения проходят; флаги отображаются
  верно; `nimble test` + `nimble cliSmoke` зелёные.

## 2. #143 — стабильные handle-ID (§35/§36)

- **Зачем:** GUI/CLI держат ссылки на объекты между пересборками графа
  (выделение, панели, undo-цепочки, автоматизация). Указатели/индексы не годятся.
- **Слой:** Core (control). handle — это **значение** (id + generation + тип),
  владелец — документ/сессия.
- **Объём:**
  - единый тип handle для узлов, параметров, компонентов, клипов, дорожек,
    размещений клипа;
  - generation-проверка: просроченный handle отвергается понятным кодом,
    а не читает чужую память;
  - адресация вложенности: путь «подграф → компонент → параметр»;
  - проекция в формат проекта (§58) и обратно при загрузке.
- **Критерии:** handle валиден после N пересборок (цикл обновлений); просроченный
  даёт ошибку (ASan/TSan чисто); тесты на ABA и двойное удаление; вложенная
  адресация видна в отчётах CLI.

## 3. #139 — Control Core: единая командная модель (§65)

- **Зачем:** CLI (#88-#90) и Editor обязаны вызывать **одни и те же команды**
  (§60). Сегодня есть только POD `EngineCommand`/`EngineMetric` в
  `core/ipc_bus.nim`; нет API «операция над проектом». Иначе CLI и Editor
  начнут дублировать логику и станут «вторым Core» (§23).
- **Слой:** Core, новый **control-слой** рядом с realtime-ядром (§66). Владелец
  документа — сессия; исполнение на control-path; realtime получает результат
  существующим путём (`postGraphUpdate`).
- **Объём:**
  - типы команд: CreateNode, DeleteNode, Connect, Disconnect, SetParameter,
    AddTrack, RemoveTrack, AddClip, DeleteClip, AddNote, DeleteNote,
    SetTransport, LoadResource (+ группы/компоненты);
  - конверт команды: идентификатор, версия API, результат — `ErrorFrame`
    (#117), а не голый `bool`;
  - транзакции: pre-check → apply → commit/rollback (#127), интеграция с
    историей (#109);
  - один путь исполнения для CLI и Editor (общий код).
- **Критерии:** одна команда даёт идентичный результат из CLI и тестового
  клиента (сравнение снапшотов/рендера); отказ на середине не оставляет
  частичных изменений; составная операция = одна запись истории; ни одна
  команда не аллоцирует/не блокирует в audio-потоке.
- **Риск:** это самый крупный блок шага; дробится на подэтапы **внутри** одной
  Issue (типы команд → транзакции → миграция CLI), отдельные ветви допустимы.

## 4. #141 — Query API чтения модели

- **Зачем:** `project show`, `node list`, `param get` (#89/#90) и Editor нуждаются
  в **чтении** живой модели (граф, треки/клипы, параметры, PDC, деградации).
  Без API каждый клиент полезет во внутренние структуры (§63) или станет читать
  файл вместо сессии.
- **Слой:** Core (control), запросы поверх снапшота (F2). Результат —
  неизменяемые DTO, не указатели. В audio-поток запросы не попадают.
- **Объём:**
  - примитивы: узлы/порты/параметры, треки/клипы, соединения, задержки и PDC,
    транспорт, деградации/обходы, состояние записи;
  - стабильные DTO с версией (совместимы с `--json` CLI и Editor);
  - фильтры и пагинация для больших проектов (1000+ узлов);
  - один источник данных для CLI и Editor (§60).
- **Критерии:** ни один запрос не требует внутренних структур; результат
  детерминирован и сортирован; CLI и Editor показывают одну картину; запрос на
  1000 узлов укладывается в бюджет UI-кадра без блокировок.

## 5. #148 — паритет «GUI-действие = команда»

- **Зачем:** CLI, диагностика и ядро должны дружить с GUI, а не бороться (§60):
  любое действие интерфейса — команда, которую можно повторить скриптом (§21/§61).
- **Слой:** Core (контракт) + CLI/Editor (клиенты). Это **правила**, а не новый
  код ядра.
- **Объём:**
  - регламент: каждое действие GUI обязано иметь CLI-эквивалент (перечень +
    тест-контроль);
  - палитра команд GUI (Ctrl+K) исполняет те же команды, что CLI;
  - «GUI → скрипт»: запись сессии действий в воспроизводимый скрипт;
  - одинаковые коды ошибок/exit-коды в CLI и GUI (#117/#121);
  - attach/detach к headless-сессии (F2) как штатный сценарий;
  - документ «границы клиентов».
- **Критерии:** сценарий из GUI воспроизводится скриптом с тем же результатом
  (golden-рендер #102); нет действий GUI без CLI-эквивалента; сообщение об
  ошибке одинаково; `<cli> --json` и GUI показывают одну модель.

## 6. #213 — встраивание ядра в сторонний движок

- **Зачем:** ядро без GUI, с POD-контрактами (§66), но **публичного API для
  встраивания, примера и сборки как библиотеки** нет.
- **Слой:** Core/Nodes (публичный API) + Commons (сборка). Встроенный хост
  владеет audio callback; RT-контракт сохраняется.
- **Объём:**
  - минимальный публичный API: создать/уничтожить движок, отправить команды,
    получить метрики, скомпилировать граф;
  - пример минимальной интеграции без GUI (граф → нода → рендер блоков → стоп);
  - сборка как библиотеки (static/dynamic) с документированными флагами;
  - guard: Core не зависит от GUI (§6);
  - лицензия/условия — без изменений.
- **Критерии:** пример собирается и работает «из коробки»; зависимости Core не
  растут; RT-контракт соблюдён.

## 7. #5 — убрать зависимость Commons → Core

- **Зачем:** Commons — нейтральный набор, не знающий про Core (§26/§27). Фактически
  `commons/audio_file_io.nim`, `commons/midi_io.nim`, `commons/waveform_cache.nim`
  тянут `core/`, а маскируется это глобальным `--path core` в `config.nims`.
- **Решение (из вариантов Issue):** перенести модули в Core
  (`core/audio_file_io.nim`, `core/midi_io.nim`), в Commons оставить `undo_redo`
  и `waveform_cache`; нейтральные типы — в Commons с реэкспортом. Выбор
  зафиксировать в PR и в MANIFEST.
- **Критерии:** `grep` не находит импортов `signal_types|wav_codec|audio_buffer`
  из `commons/`; `nimble test` зелёный; формулировка про допустимые зависимости
  Commons уточнена в MANIFEST.

## 8. #50 — architecture guards направления зависимостей

- **Объём:**
  - guard: `core/` не импортирует `adapters/`;
  - guard: `nodes/` не импортирует `adapters/clap|eut|portaudio|rtmidi`;
  - guard: `commons/` не импортирует `core/` (включается блокирующим после #5);
  - сопоставлять только строки импорта, а не подстроки в комментариях.
- **Критерии:** job `architecture` падает на искусственном `import adapters/x`
  в `core/` и проходит на текущем дереве; шаблон PR упоминает guard; в README —
  строка, как воспроизвести guard локально.
