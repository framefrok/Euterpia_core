# Клиенты EUTERPIA: границы паритета CLI и Editor

CLI и Editor — **равноправные клиенты Core** (MANIFEST §60), а не «настоящий
продукт» и «урезанная игрушка». Значит, поверхность действий должна быть одна:
то, что собирается мышью, обязано воспроизводиться скриптом, и наоборот —
действие, у которого нет командной пары, не должно появляться в интерфейсе
вообще (§61 headless-first, §65 командная модель).

- Источник правды о перечне действий — `core/control/actions.nim`.
  Палитра окна, горячие клавиши и запись сессии строятся из него, а не из
  собственных списков: два списка разошлись бы на первом же новом действии.
- Источник правды о командах CLI — спецификация `libs/cli_spec` (#330),
  которую печатает `euterpia help --json`.
- Чтение модели клиент ведёт через **Query API** (`core/control/query.nim`,
  #336): неизменяемые DTO, устойчивый порядок, один и тот же ответ у CLI и
  Editor. Обход коллекций документа запрещён проверкой
  `tools/check_architecture.py` (`nimble archGuard`): в ней поимённо
  перечислены лишь валидаторы целостности и пути записи.
- Проверка паритета — `nimble cliSmoke`, suite «паритет клиентов» в
  `tests/cli_test.nim` (issue [#148](https://github.com/framefrok/Euterpia_core/issues/148)).
- Справочник по CLI: [cli.md](cli.md). Встраивание ядра в чужой хост:
  [embedding.md](embedding.md).

## Что клиент делает и чего не делает

Клиент — это **ввод**, а не логика (§64):

```text
Input → Command → Core → State update → Render
```

Отсюда границы, одинаковые для CLI и Editor:

- клиент **не считает** аудио, не компилирует граф и не управляет DSP (§20) —
  это делает ядро, а команда только меняет модель или состояние;
- клиент **не трогает внутренние структуры** Core: ни указатели, ни память
  состояния, ни бинарный формат (§63). Обе стороны ходят через
  `core/control` (документ) и публичный API движка (транспорт);
- клиент **не изобретает** команд: добавить действие в интерфейс, не добавив
  команду, нельзя — перечень в `core/control/actions.nim` один на всех.

## Области действия

Область говорит, **что именно меняется** действием, и потому определяет и
откат, и пару.

| Область | Что меняет | Команда ядра | Откат |
|---|---|---|---|
| `edit` | документ | команда `ControlCommandKind` (§65) | есть, через историю (#109) |
| `runtime` | состояние исполнения, документ не тронут | процедура движка (`audio_engine.post*`) | нет — состояние не документ |
| `io` | файлы проекта и экспорта | нет | нет |
| `view` | ничего: показывает (§21) | нет | нет |
| `session` | настройки и диагностику окружения | нет | нет |
| `window` | само окно: палитра, раскладка, attach | нет, и быть не может | нет |

Практическое следствие первой строки: «нажал Play» **не делает проект
грязным**, а «задал темп» — делает. Именно поэтому `transport.play` лежит в
`runtime`, а `transport.set` — в `edit`.

## Правила паритета

1. **`issue == 0` — действие поставляется целиком.** У него есть команда CLI
   из реестра CLI, а если оно меняет документ — ещё и **реализованная** команда
   control-слоя. Незакрытый разрыв обязан быть номером issue, а не тишиной.
2. **`issue > 0` — поставляется частями.** Номер issue обязателен: без него
   «запланировано» неотличимо от «забыто». Сегодня такие разрывы — транспорт
   (#257, #92), секвенсор (#87), стемы (#108), окно (#148).
3. **Обратная сторона та же.** Каждая видимая команда CLI либо покрыта
   действием (у действия указано её имя), либо объяснена в `cliOnlyCommands`
   с причиной. Команда, не попавшая ни туда, ни сюда, валит тест.
4. **Реализованная команда документа обязана быть доступна из интерфейса** —
   иначе команда ядра есть, а пары у неё нет. Исключение — откат
   (`ccRestoreNodeState`): он внутренний и приходит из истории, а не из палитры.
5. **`window` из правила 1 исключено, но не молча.** Действию окна команда
   ядра не нужна по построению (палитра, раскладка, attach), однако без
   номера issue такое действие в перечень не попадает.

## Команды только для CLI

Это решение, а не пробел: у окна нет оболочки, поэтому некоторые команды
существуют только в CLI. Каждая объяснена, и объяснение проверяется тестом.

| Команда | Почему без действия интерфейса |
|---|---|
| `completion` | автодополнение оболочки: у окна нет оболочки, дополнять нечего |
| `help` | справка печатается в окне; в GUI это палитра и меню, а не команда |
| `version` | версия показывается в окне «О программе», а не выполняется |


## Что проверяет тест паритета

Suite «паритет клиентов» в `tests/cli_test.nim` (`nimble cliSmoke`) сверяет
перечень с **опубликованной** поверхностью CLI (`euterpia help --json`), а не с
внутренними таблицами команд — так проверка не может «сойтись» на общей ошибке:

- id действий уникальны, а человеческие подписи непусты;
- у действия с `issue == 0` есть команда CLI из реестра, а если оно меняет
  документ — ещё и реализованная команда control-слоя (`isImplemented`);
- имя CLI-команды любого действия существует в `help --json` (ловит опечатку
  и удалённую команду);
- каждая видимая команда CLI покрыта действием либо объяснена в
  `cliOnlyCommands`, причём причина непуста;
- каждая реализованная команда документа покрыта действием (кроме отката);
- имена процедур движка у `runtime`-действий действительно объявлены в
  `core/audio_engine.nim`;
- таблицы этой страницы полны: id каждого действия и имя каждой CLI-only
  команды присутствуют в тексте документа.

## Сценарий, который обязан работать без окна

Из §19 и §62: проект создаётся, изменяется и рендерится без Editor.

```bash
euterpia init demo.eproj --name Demo --tempo 120
euterpia node add osc demo.eproj
euterpia node add gain demo.eproj
euterpia connect 1:out 2:in demo.eproj
euterpia param set 1 freq 330 demo.eproj
euterpia graph check demo.eproj
euterpia render demo.eproj --out out.wav --seconds 2
euterpia --json node list demo.eproj
```

Расширение проекта — `.eproj` (`docs/cli.md`); историческое `.eut` принимается
наравне, потому что ядро определяет тип файла по содержимому, а не по имени.

Те же шаги в окне — это те же действия (`graph.node.add`, `graph.connect`,
`param.set`, …), а не вторая реализация: они видны в палитре и записываются в
скрипт (`window.recordScript`). Обратное тоже верно: записанный скрипт
воспроизводит сессию один в один, потому что действие и команда CLI сводятся к
одному вызову ядра (#139).

## Где это ещё не сошлось

Честный список разрывов; каждый закрывается своим issue, и до закрытия он
виден в `core/control/actions.nim` номером, а не забыт:

- транспорт: `transport` (CLI #257) уже несёт темп/размер/позицию/цикл и
  offline-состояние; живой путь (`play`/`pause`/`stop`/`seek` на реальном
  устройстве) и реализация команды документа `transport.set` в control-слое —
  за #92 и #257 соответственно;
- секвенсор: команды дорожек, клипов и нот объявлены и отвечают
  `ecUnsupportedCommand`, CLI-команд для них нет (#87);
- стемы и батч-рендер: действие объявлено, пути исполнения нет (#108);
- окно: палитра, запись сессии и attach (F2) появятся вместе с Editor
  (линия v0.4 — фундамент и скелет GUI, #152).
