# libs/ — библиотеки EUTERPIA

Здесь живут **наши библиотеки** — переиспользуемый код верхнего слоя, который
строится поверх Core и Nodes и которым пользуются CLI, Editor и прикладные
программы (например, генераторы композиций). Ни Core, ни Nodes о `libs/` не
знают: зависимости идут строго в одну сторону (`Core ← Nodes ← libs ← CLI`).

## Что здесь есть

| библиотека | назначение |
|---|---|
| `compose/` | «композиция как код» (#285): модель партитуры и сборка `.eproj`-проектов из Nim |
| `midi_export` | проект → Standard MIDI File: один файл или по файлу на инструмент |
| `cli_spec` | описание команд CLI данными (#330): справка, `--json`-схема, автодополнение и `docs/cli.md` из одного источника |
| `script` | сценарий как файл (#333, #335): команды control-слоя, переменные, план, транзакция и эталон рендера |
| `presets` | шаблоны, сет-листы и пресеты параметров как данные (#341–#343): проверка по реестру, применение транзакцией и сборка «как обычно» |
| `watch` | наблюдение за файлами проекта (#344): снимки, дебаунс и ограничение частоты рендеров как чистые правила |

## `midi_export`

Единственное место, где видны сразу и проект (`core/project`), и кодек
(`commons/midi_io`): ядру запрещено импортировать Commons, а кодек нейтрален
и про проект не знает. Отсюда `toSmf`, `writeMidi` (формат 1: дорожка-дирижёр
с темпом и размером + по дорожке на партию) и `writeMidiTracks` (по файлу на
инструмент). Позиции не пересчитываются — тики проекта и SMF совпадают;
клипы раскрываются ровно так, как их играет движок. CLI-команда —
`euterpia midi`.

## `cli_spec`

Описание команды CLI — **данные**, а не текст: `CommandSpec` (имя, синопсис,
позиционные аргументы, ключи с видом `value`/`switch`, типом значения,
умолчанием и обязательностью, варианты аргумента, пример вызова, поля ответа
`--json`). Из одной спецификации собираются человеческая справка (`--help`),
машинная схема (`help --json`), кандидаты автодополнения (`__complete`) и
раздел справочника `docs/cli.md`.

Библиотека знает о **форме** команд и ничего не знает о ядре, разборе argv
или о том, что команда делает: тело команды остаётся в CLI
(`cli/registry.nim` соединяет `spec` с `run`), поэтому `cli_spec` не тянет
`euterpia_version` и получает имя CLI параметром.

`validateSpecs` проверяет описания (синопсис, ключи, типы значений,
умолчания, вариант аргумента, пример, поля), `spliceReference` вставляет
сгенерированный раздел между маркерами `cli-spec:begin`/`cli-spec:end`, а
`markdownReference` печатает сам раздел. Полнота описаний и совпадение
раздела в репозитории с генератором проверяются в CI (`nimble cliSmoke`), а
поведение проверки на испорченном описании — unit-тестами
(`tests/unit/test_cli_spec.nim`).

## `script`

Сценарий — **последовательность команд control-слоя** (`ControlCommand`),
сохранённая в JSON (`euterpia.script`, версия 1). Библиотека знает о форме
сценария и ничего не знает о CLI: файл, argv и печать остаются в клиенте.

- `parseScript` / `encodeScript` — разбор и каноническая запись; чужая версия
  и неизвестная команда отвергаются кадром ошибки, а не читаются молча;
- переменные (`variables`, `${имя}`) подставляются **с типом**: строка ровно
  из `"${freq}"` заменяется значением-числом, остальное — текстом; неизвестная
  переменная называется вместе с адресом места;
- `previewScript` — план без побочных эффектов (принимает документ по
  значению), `applyScript` — одна транзакция с обратными командами из ядра;
- `baseDocument` — пустой документ с метаданными шаблона (сборка «с нуля»,
  #416), `lossReport` — что текущий проект содержит, а сценарий не выражает;
- `diffSummary` — «что изменится» счётчиками сущностей, а не сравнением
  файлов руками;
- `Baseline` — эталон рендера (#335): метрики, SHA-1 файла, сценария и
  сэмплов; сравнение возвращает список различий, а обновление эталона —
  отдельная явная операция клиента.

Детерминизм держится на внедрённых часах документа: сценарий не читает
системное время, поэтому повтор на том же проекте даёт побайтово тот же
документ. CLI передаёт часы из поля `stamp` сценария или из прежней отметки
проекта (`cli/control_bridge.openDocumentAt`).

## `presets`

Заготовки — **данные**, а не примеры кода (#341–#343). Три формата узнаются по
полю `format`, а не по расширению (§19/§58):

- `euterpia.preset` v1 — шаблон проекта: ноды с параметрами, связи по именам
  нод, дорожки с необязательной партитурой. Порядок нод задаёт их id;
- `euterpia.setlist` v1 — сет-лист: имя шаблона и партии (роль, клип, ноты,
  сведение голоса);
- `euterpia.param-preset` v1 — пресет параметров: тип ноды, необязательная
  роль и значения.

`validatePreset`/`validateSetlist`/`validateParamPreset` проверяют заготовку по
**реестру нод** до применения: неизвестный тип — `not_found`, параметр вне
диапазона — `invalid_argument`, шаблон без однозначного мастер-выхода
отвергается. `presetCommands`, `setlistCommands` и `paramPresetCommands`
превращают данные в команды control-слоя, поэтому применение — обычная
транзакция: отказ не оставляет следов, `undo` отменяет её целиком.

Файлы ищутся в `presets/templates|setlists|params`, рядом с бинарём, в
`EUTERPIA_PRESETS` и `~/.config/euterpia/presets`; `catalogOf`/`findPreset`
возвращают и сломанные файлы отдельным списком, а не прячут их.

## `watch`

Наблюдение за файлами проекта — **правила**, а не `sleep` (#344). `WatchFile`
хранит «есть/нет, mtime в наносекундах, размер»; `changedPaths` сравнивает
снимки по пути; `watchStep` принимает решение по подставным часам:
изменения копятся в одну серию, рендер идёт после `debounceMs` тишины и не
чаще `minIntervalMs`. Поэтому «две быстрые правки — один рендер» проверяется
unit-тестом без файловой системы и без ожидания. `watchPoll` — тонкая обёртка,
которая сканирует диск; `watchPaths` собирает список (проект, сценарий,
соседние `*.notes`/`*.eus`, явные файлы). Рендер, Ctrl-C и атомарная запись
WAV остаются в CLI: библиотека не знает ни о аудио, ни о терминале.



- `score` — музыкальная модель (события, такты, мотивы) с приёмами развития
  (транспозиция, увеличение) и выводом в текстовую нотацию ядра;
- `builder` — низкоуровневая сборка **произвольного** проекта: ноды любых
  типов, связи любых видов, дорожки — из описателей типов (#300);
- `song` — высокоуровневая раскладка «партии + сумматор» → `ProjectFormat`;
- `midi` — MIDI-экспорт раскладки: один файл или по файлу на партию
  (обёртки над `midi_export`);
- `engine` — рендер прямо из кода: `render(arr, wav)` через `loadScene` +
  `renderToWav` (без `build.sh` и CLI) (#300).

Полное руководство и каталог инструментов — **[docs/libs/compose](../docs/libs/compose/README.md)**.

Почему на Nim, а не скриптом: проект — это данные Core (`core/project`), и
генерировать их лучше тем же типом, что и читает ядро. Это исключает
расхождение форматов, даёт проверки компилятора и не тянет внешних
зависимостей.

Примеры — `compositions/dark-fantasy/generate.nim` («Cathedral of Ash»,
medieval dark fantasy) и `compositions/neo-romantic/generate.nim`
(неоклассический ансамбль). Обе пьесы собираются библиотекой и, для сверки, тем
же составом только через CLI (см. `build_via_cli.sh` рядом) — результат
совпадает.
